深入理解 RN 与 Native 交互：从 JS 调用到原生实现的完整链路

PUBLISHED 2026.08.14
iOS React Native TurboModule JSI Objective-C

最近在维护翻译历史功能时，我遇到一个非常典型的跨端协作问题：

React Native 侧的语种配置查询桥接接口从 resolveLanguageOption（单语种）切换成了 getTranslationLanguageConfigs（批量 TurboModule），但 iOS 原生侧没有跟上实现，导致 RN 调用时静默失败、界面降级。

顺着这个问题，我把 RN 与 Native 交互的完整链路彻底拆了一遍。这篇文章不讲 API 用法，而是回答几个「怎么找到的」问题：

  • JS 调用 TurboModule 方法时，运行时是怎么找到 Native 实现的？
  • 生成代码里的 @selector(...) 是怎么和 TS 接口对应上的？
  • Bridge 库（RNBridgeLib）怎么在不依赖主工程的情况下，调用主工程的业务能力？
  • 反过来，Native 有状态变化时，又是怎么主动通知 JS 的？

一、为什么需要「桥」：两个世界，两种语言

任何一个 iOS 上的 RN 工程，运行时的内存里都住着两个世界：

flowchart LR
    subgraph JS世界[JS 世界]
        A[JavaScript 引擎<br/>Hermes / JSC]
        B[React 组件<br/>业务逻辑]
    end

    subgraph Native世界[Native 世界]
        C[Swift / Objective-C<br/>系统框架]
        D[网络 gRPC / 蓝牙 / 语音<br/>系统能力]
    end

    A --- E[桥 Bridge]
    B --- E
    E --- C
    E --- D
  • JS 世界：页面 UI、布局、交互逻辑，跑在 JS 引擎里，只会说 JavaScript；
  • Native 世界：系统能力（网络、蓝牙、语音、存储），跑在系统运行时里，只会说 Objective-C/Swift。

JavaScript 永远不能直接调用 Swift 的方法——就像两个各说各话的人。React Native 提供了一座「桥」：JS 能打电话给 Native，Native 也能回电话给 JS。而这座桥在不同的架构代际里，实现方式完全不同。

老架构 Bridge：消息队列 + 序列化

老架构里，JS 调用 Native 的过程是：

  1. JS 把方法名和参数序列化成 JSON，丢进一个异步消息队列；
  2. Native 侧从队列里取消息，反序列化，再调用对应的原生方法；
  3. 结果再序列化、入队、回传。

这个过程有两个固有瓶颈：每次调用都要 JSON 序列化/反序列化，而且消息是异步批处理的，有额外延迟。这就是老桥被诟病「慢」的根本原因。

新架构 TurboModule + JSI：JS 直接调 C++

新架构（New Architecture）的 TurboModule 用 JSI（JavaScript Interface） 取代了消息队列：JS 引擎通过 JSI 直接调用 C++ 函数，不需要 JSON 序列化，不需要异步排队。

但无论新旧，核心问题不变：JS 侧如何「按名字」找到 Native 侧的实现？下面用真实的代码逐层拆解。

二、第一跳：JS 怎么找到 TurboModule？

2.1 TS 接口：Codegen 的「输入」

这里发生了两件事：

  1. 声明接口：Spec 告诉 Codegen「这个模块有一个方法 getTranslationLanguageConfigs，入参是 string 数组，返回 Promise」——这是后续所有生成代码的依据；
  2. 获取模块对象：TurboModuleRegistry.get('RNTranslationModule') 用名字在 Native 的模块注册表里查对象，拿到后业务代码就能 await module.getTranslationLanguageConfigs(codes) 了。

这个名字是全链路第一个匹配点：JS 侧 get('RNTranslationModule') 必须和 Native 侧 moduleName 返回的字符串一字不差，否则拿到 null。

invokeObjCMethod 拿到写死的 selector 后，用 OC 运行时真正调用：

OC 的 @selector 就是方法的名字（门牌号）。对象根据它找到自己类里签名一致的方法体——找不到，调用就失败。这正是之前 iOS 侧缺实现时的状况：selector 存在，但没有实现体去响应它。

3.2 小知识：OC 的 selector 到底是什么

selector 不是函数、不是实现，就是方法的名字。把对象比作一栋楼，方法是房间：

概念 类比
方法实现 房间里的内容（真正干活的人）
selector 门牌号（”301 室”）
@selector(...) 写出门牌号的语法
performSelector 按门牌号找房间进去

注意 OC 方法名的冒号规则：方法名 = 方法名 + 每个参数的冒号。getTranslationLanguageConfigs:resolve:reject: 有三个参数，就有三个冒号。门牌号写得越详细，越不会找错房间。

sequenceDiagram

    participant REG as TurboModuleRegistry
    participant JSI as JSI 层（Codegen 生成）

五、第三跳：Bridge 库怎么调用主工程？（AppRouter 运行时路由）

5.1 一个绕不开的问题：依赖方向

再看一眼架构，会发现一个矛盾：

  • 主工程依赖 RNBridgeLib：主工程能用 RNBridgeLib 里的类；
  • RNBridgeLib 不能依赖主工程：否则循环依赖，编译不过。

但问题来了：RN 模块（在 RNBridgeLib 里）需要调用业务能力（在主工程里）——比如查语种配置的 TranslationLanguageConfigStore 在主工程。RNBridgeLib 直接引用主工程生成的 Swift 桥接头文件，就会导致循环依赖。

5.2 解法：喊一嗓子路由，让宿主接听

AppRouter 就是来解决这个矛盾的。RNBridgeLib 不直接调用主工程，而是喊一嗓子路由：

5.3 AppRouter 的运行时调度原理

AppRouter 的路由机制（AppRouter.m，来自 Pod AppUtils）是一个纯 OC 运行时动态派发，没有编译期绑定：

为什么主工程能响应？ 因为 OC 的 category（分类）机制：主工程的 AppRouter+Translate.m 写着 @implementation AppRouter (Translate)，编译链接后，这个方法并入 AppRouter 类本身。运行时问「AppRouter 有没有 routerForTranslateLanguageConfigs:completion: 这个方法？」→ 有。

5.4 小知识：OC 的 category 是什么

category = 不修改原类源码，给一个现成类「追加方法」的机制。

AppRouter 是第三方库（Pod）里的类，你不能拆了重建，但可以在旁边「加盖一层」——category 方法编译后并入原类，运行时看就是一个类。

你们项目里全是这种模式：

每个业务模块给 AppRouter 加一层「自己的分机」，互不干扰，也不改动 AppRouter 本体。

5.5 为什么用运行时路由：三个实打实的好处

  1. 打破循环依赖（最重要）：库 → 宿主方向解耦，RNBridgeLib 保持纯净、可独立编译、可被其他 App 复用；
  2. 按业务模块横向扩展：加 AppRouter+Translate、AppRouter+Glasses，各加各的 category，不需要改 RNBridgeLib 或 AppRouter 本体；
  3. 运行时才决定谁响应（可插拔）：respondsToSelector 是运行时检查——主工程没实现某路由时，canOpenRouter 返回 NO，调用方可以提前判断；也支持在 AppRouterMap.plist 里自定义 selector 映射，路由可配置。

关键点：返回给 JS 的东西必须是「能序列化的数据」——字符串、数字、布尔、数组、字典（JSON 能表达的东西）。Swift 的 struct、对象要先转成 JSON 字符串/字典，JS 才能理解。

这里的 resolve / reject 就是 Promise——JS 里「异步等结果」的语法：

  • Native 成功 → 调 resolve(结果) → JS 的 await 拿到值
  • Native 失败 → 调 reject(错误) → JS 抛异常，被 catch 捕获

八、反向交互：Native 怎么主动通知 JS？

前面讲的都是「JS 主动打电话给 Native，等结果」。但真实场景里还有大量反向需求：Native 侧的状态变了（蓝牙断开、登录状态变化、车控数据更新……），Native 要主动把消息推给 JS，而不是等 JS 来问。这就是事件（Event）机制。

8.1 一个管所有事件的中枢：EventEmitterManager

你们项目里有个 EventEmitterManager（RNBridgeLib），它把 Native 侧的各种状态变化统一转成 RN 事件。核心思路：Native 内部用 NSNotificationCenter 发通知，EventEmitterManager 监听这些通知，再转成 sendEventWithName:body: 发给 JS：

8.2 关键点 1：supportedEvents 先声明，hasListeners 再确认

  • supportedEvents：Native 声明「我能发这些事件」，相当于先挂出分机列表；
  • startObserving / stopObserving：JS 侧第一次 addListener 时触发 startObserving（hasListeners = YES），最后一次移除监听时触发 stopObserving（hasListeners = NO）；
  • sendNoticeWithEventName: 里先判 hasListeners：JS 没在听就别发，避免空转。

8.3 关键点 2：事件名就是 JS 和 Native 之间的”暗号”

事件名必须两端一致。Native 侧发什么名字，JS 侧就监听什么名字：

8.4 两种监听方式：DeviceEventEmitter vs NativeEventEmitter

方式 适用 特点
DeviceEventEmitter 全局事件（你们项目主要用这个） 不需要拿到模块实例，addListener('名字') 直接听
NativeEventEmitter 某个特定模块的事件 需要先 new NativeEventEmitter(module) 再监听，更精准

8.5 Native → RN 完整时序

sequenceDiagram
    participant NS as NSNotificationCenter
    participant EM as EventEmitterManager (Native)
    participant JS as RN 组件
    participant BUS as DeviceEventEmitter

    JS->>BUS: addListener('BleRssiChanged')
    BUS-->>EM: startObserving (hasListeners = YES)
    Note over NS,EM: 蓝牙信号变化…
    NS->>EM: postNotification BleRssiChanged
    EM->>EM: dispatchToRN: 转数据
    EM->>BUS: sendEventWithName('BleRssiChanged', body)
    BUS-->>JS: 回调触发，更新 UI

8.6 对比：调用（RN→Native）vs 事件（Native→RN）

维度 调用（Promise） 事件（Event）
方向 JS 主动 → Native，等一次结果 Native 主动 → JS，可多次
语义 请求/响应（一问一答） 订阅/推送（持续广播）
是否需要返回值 是（resolve/reject） 否（fire and forget）
JS 侧写法 await module.method() DeviceEventEmitter.addListener(...)
典型场景 查语种配置、gRPC 请求 蓝牙断开、登录态变化、车控数据

两者互补：RN 与 Native 交互 = 「调用」解决一问一答（JS 问，Native 答），「事件」解决持续推送（Native 有变化就广播，JS 订阅收听）。

九、全景总览与核心结论

把整个调用链画成一张图：

flowchart TB
    subgraph JS侧[JS 世界]
        A[业务代码<br/>TranslationLanguageConfig.ts]
        B[TurboModuleRegistry.get<br/>'RNTranslationModule']
    end

    subgraph 胶水层[Codegen 生成层]
        C[methodMap_ 方法名 → C++ 函数]
        D[@selector 写死绑定]
    end

    subgraph 库层[RNBridgeLib 转发层]
        E[RNTranslationModule.mm<br/>moduleName 注册 + 方法实现]
        F[AppRouter openRouter]
    end

    subgraph 主工程[宿主 App 业务层]
        G[AppRouter+Translate.m<br/>category 并入 AppRouter]
        H[TranslationLanguageConfigBridge<br/>Swift @objc 桥接]
        I[TranslationLanguageConfigStore<br/>数据源]
    end

    A --> B --> C --> D --> E --> F --> G --> H --> I
    I --> H --> G --> F --> E --> D --> C --> B --> A

核心结论：

层 机制 「找到」靠什么
JS → C++ TurboModule + JSI 模块名字（get('RNTranslationModule') ↔ moduleName）
C++ → OC 实现 生成代码 invokeObjCMethod Codegen 写死的 selector + OC 运行时按 selector 找方法体
OC 库 → 主工程 AppRouter 路由 运行时拼 selector 名 + category 把方法并入类 + respondsToSelector
数据返回 Promise resolve/reject JSON 可序列化数据原路回传

一句话总结：整个调用链是「JS 报名字 → 编译期写死的表找到 OC 方法 → OC 运行时现场拼路由名找到主工程业务 → Swift 干活 → JSON 原路返回」。理解了这两跳（TurboModule 跨语言 + AppRouter 跨模块），你就理解了 RN 与 Native 交互的骨架。

十、踩坑记录：一次桥接契约不一致的完整复盘

回到开头的问题——接口切换后 iOS 侧发生了什么：

  1. RN 侧：eff0549fb6 把语种查询从旧的 resolveLanguageOption（单语种 RCT Bridge）切换为 getTranslationLanguageConfigs（批量 TurboModule），并更新了 TS 接口声明；
  2. Codegen 侧：重新生成后，RNModule.h 里出现了新 selector 的协议声明，methodMap_ 里也有了新方法的 C++ 函数——但实现类里没有方法体；
  3. iOS 侧后果：JS 调用 getTranslationLanguageConfigs → 胶水代码按写死的 selector 找方法体 → 找不到，Promise reject → RN 侧 catch 后静默降级为空配置 → 语种名显示 code、RTL 布局失效、disable 识别不了。

修复就是补齐两块拼图：

  • RNBridgeLib 实现层：在 RNTranslationModule.mm 补上 getTranslationLanguageConfigs:resolve:reject:，经 AppRouter 转发；
  • 主工程路由层：新增 AppRouter+Translate.h/.m，实现 routerForTranslateLanguageConfigs:completion:，用现有数据源批量查询并返回 JSON。

这次的教训：跨端协作时，桥的「契约」由 RN 侧 TS 接口 + Native 侧 selector 实现共同构成，任何一侧改动都必须同步另一侧，否则就是运行时静默失败——而这类失败在开发期很难察觉，因为 RN 侧往往有兜底降级。
