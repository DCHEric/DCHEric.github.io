从 H5 到 gRPC：看懂浏览器、Node.js BFF 与 iOS 的两种后端调用方式

PUBLISHED 2026.08.14
gRPC Protobuf iOS Node.js H5 BFF

iOS 已经升级了最新的 gRPC APIs，可以直接读取后端新增字段；为什么 H5 仍然拿不到？H5、WebServer 和真正的后端之间，到底经过了哪些网络请求？

顺着这个问题继续追下去，又会遇到更多疑问：

  • 浏览器为什么不和 iOS 一样直接调用 gRPC？
  • WebServer 是不是只做了一次“转发”？
  • iOS 为什么必须把 .proto 编译成 Swift 代码？
  • Node.js 没有生成 TypeScript gRPC 代码，开发时又怎么调用接口？
  • APIs 通过 Git submodule 引入以后，构建和运行阶段分别发生了什么？

本文就从这些基础问题出发，把整条链路拆开说明。

四、浏览器为什么不直接调用普通 gRPC

iOS 可以集成原生 gRPC SDK，建立 HTTP/2 连接、发送 Protobuf 二进制数据，并处理 TLS、Token 和 metadata。

浏览器的网络能力和安全模型不同，不能像原生 App 一样随意使用普通 gRPC Client。浏览器如果要直连 gRPC，通常需要额外建设：

  • gRPC-Web 客户端；
  • Envoy 或其他协议转换网关；
  • 浏览器跨域配置；
  • 面向公开网络的鉴权方案；
  • 对应的 TypeScript Protobuf 代码生成与打包流程。

分享页还有一个特殊之处：访问者可能没有登录，甚至没有安装 App。此时如果直接暴露内部 gRPC 服务，服务地址、鉴权方式和访问控制都会变得更复杂。

因此，常见做法是在浏览器和真正后端之间增加一个 BFF（Backend for Frontend）：

BFF 不只是简单转发，它通常还负责：

  • 解析或解密分享参数；
  • 校验分享内容能否访问；
  • 隐藏内部服务地址；
  • 补充服务端鉴权和 metadata；
  • 调用内部 gRPC 服务；
  • 把 Protobuf 响应转换成浏览器可用的 JSON；
  • 控制最终暴露给公网的数据范围。

十二、静态代码生成与动态加载怎么选

维度 iOS 静态生成 Node.js 动态加载
协议使用时间 App 编译前 服务启动时
产物 Swift 消息类型和 Client 内存中的动态 Client
类型安全 强，很多错误编译期发现 相对弱，部分错误运行时发现
IDE 自动补全 完整 取决于手写类型
生成文件维护 需要 不需要
协议升级 更新生成的 Swift APIs 更新 .proto / submodule
运行时是否需要 .proto 通常不需要 需要

两种方式没有绝对的好坏：

  • 移动端更重视强类型、编译期检查和固定产物，静态生成更自然；
  • Node.js 服务更强调快速接入和减少生成文件，动态加载比较灵活；
  • 如果 Node.js 项目规模变大、接口很多，也可以改为 ts-proto 等静态生成方案，提高类型安全。

十三、排查类似问题的实用顺序

以后再遇到“App 有字段，但 H5 没字段”，可以按照下面的顺序检查：

  1. 真正后端是否已经返回该字段；
  2. iOS 和 WebServer 分别使用哪个 APIs 版本；
  3. WebServer 的 .proto 是否已经包含该字段编号和类型；
  4. CI 是否正确更新 submodule；
  5. Docker 镜像是否包含新版 apis/；
  6. 测试环境是否部署了新镜像；
  7. 浏览器 Network 中实际命中了哪个环境；
  8. HTTP Response 是否已经包含字段；
  9. H5 数据转换层是否又把字段丢弃了；
  10. 页面是否真正消费和展示了这个字段。

其中，第 8 步和第 9 步很容易混淆：

  • Network Response 有字段，页面没有：问题在 H5 解析或渲染；
  • Network Response 没字段：继续检查 WebServer、协议版本和真正后端。

总结

整套架构最终可以收敛成四句话：

  1. H5 仓库发布的是静态资源，真正发请求的是浏览器。
  2. 浏览器通过 HTTP/JSON 请求 BFF，BFF 再通过 gRPC/Protobuf 请求真正后端。
  3. iOS 把 .proto 提前生成 Swift 代码；Node.js 可以选择启动时动态加载 .proto。
  4. 动态加载并不等于不依赖 APIs；WebServer 必须把正确版本的 .proto 带进镜像，才能正确编码和解码新字段。

理解“谁在发请求、谁在读取 .proto、协议在什么时间被转换”之后，H5、BFF、gRPC、submodule 和移动端 APIs 之间的关系就不再神秘了。
