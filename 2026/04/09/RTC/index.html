PUBLISHED 2026.04.09

从“实时通话”到“实时智能交互总线”：一套移动端 RTC 架构实践

在大语言模型进入实时交互场景之后，RTC 的角色已经发生了明显变化。它不再只是一个负责传输音频或视频的底层通道，而开始承担起 实时语音输入、模型流式响应、语音播报、多模态上下文同步以及工具调用协同 的基础设施职责。

尤其是在“用户说一句话，模型边理解边回复，端侧还要持续处理设备状态、拍照结果、工具执行结果”的场景里，RTC 实际上服务的已经不是传统通话，而是一种 面向大语言模型的实时对话系统。

也正因为如此，当 RTC 要同时承载语音助手、可穿戴设备、多模态输入和工具调用时，系统设计的重点就不再是“把通话接起来”，而是如何构建一条稳定、可扩展、可观测的实时智能交互链路。

这个 RTC 在业务里到底承担什么角色

如果只看 RTC 这个名字，很容易把它理解成“实时通话”或者“音视频能力”。但从实际实现来看，它在业务里承担的角色要更具体：它是整条实时 AI 对话链路的统一通道和编排器。

具体落到几条主链路上，它分别在做这些事情：

  • 负责建立一轮新的语音会话；
  • 负责把“当前角色是谁、当前是否静音、当前 topic 是什么”一起带上去；
  • 负责把 ASR、回复、建连成功这些实时结果再回给 4O UI。

2. 在眼镜场景里，它负责把“眼镜 ↔ 云端助手 ↔ 眼镜”整条链路打通

  • 接住眼镜上行音频；
  • 建立到云端的实时会话；
  • 接回云端下发的 TTS 音频和事件；
  • 再把音频、打断指令、工具调用结果转回眼镜。

3. 在视频预览场景里，它负责建连和设备控制

  • 切换前后摄；
  • 在连接状态变化时回调给页面更新 UI。

4. 在拍照记场景里，它负责把“照片上下文”带进 AI 会话

拍照记这个场景里，RTC 还不只是传音频。

也就是说，在这个业务里，RTC 干的是：

  • 把最近拍照的上下文带进本轮对话；
  • 把工具列表暴露给云端智能体；
  • 把工具执行结果继续回传给当前会话；
  • 把“拍照”和“记笔记”这两个原本分离的动作串成一条实时业务链路。

所以，如果要用一句业务话概括这套 RTC：

它不是纯媒体模块，而是角色化对话、外设语音、拍照记、视频场景共同复用的“实时 AI 会话底座”。

一、背景：为什么传统 RTC 思路不够用了

很多团队在谈 RTC 时，默认讨论的是这些问题：

  • 如何建连；
  • 如何采集麦克风；
  • 如何回放远端音频；
  • 如何处理弱网和重连。

这些当然都重要，但在智能交互场景里，RTC 面临的问题已经变了。

一条“实时会话链路”里，往往同时存在：

  • 用户实时语音输入；
  • 语音识别（ASR）；
  • 大模型对话结果；
  • 语音播报（TTS）；
  • 设备状态、定位、上下文信息；
  • 工具调用请求与执行结果；
  • 手机、可穿戴设备、摄像头等多终端协同。

这时 RTC 就不再只是“媒体通道”，而更像是一个 实时智能交互总线：

  • 媒体流在里面跑；
  • 控制流也在里面跑；
  • AI 事件流同样在里面跑；
  • 业务上下文还要在会话期间持续更新。

如果还是按照传统“通话 SDK 接个页面”的思路设计，系统很快就会变得混乱：媒体链路和业务链路纠缠、状态分散、扩展困难、问题难排查。

所以本文要讨论的核心不是“如何接一个 RTC SDK”，而是：

如何把 RTC 设计成实时 AI 会话的承载层。

二、这类系统真正难的是什么

在这类项目里，真正的复杂度往往不来自某个单点，而来自多个目标同时成立：

1. 一套 RTC，要服务多种场景

同一套能力既要支持：

  • App 内的语音助手对话；
  • 可穿戴设备唤醒后的语音问答；
  • 带视频预览的实时互动场景。

2. 一条链路里，要同时承载媒体、事件和上下文

用户说话后，并不只是“把音频送上去”这么简单，还会串起：

  • 录音数据上行；
  • VAD 事件；
  • ASR 结果；
  • 模型回复；
  • TTS 音频；
  • 打断、拒识、结束、拍照、表情等事件；
  • 工具调用和工具结果回传。

3. 可穿戴设备接入，会改变整个媒体模型

一旦加入眼镜、耳机、座舱设备等外设，App 不再是“自己采集、自己播放”，而是要承担：

  • 设备音频的接入和转发；
  • 连接未完成时的缓存补发；
  • 打断时的 buffer 清空；
  • 端到端时延统计。

4. 智能体不是静态的，会话上下文必须动态更新

在一个会话内，系统可能还要不断注入新信息：

  • 定位变化；
  • 当前绑定车辆或设备；
  • 刚拍到的图片；
  • 当前使用的角色设定；
  • 本次会话允许调用的工具集。

这意味着 RTC 层必须具备“会中更新上下文”的能力。

三、一个可落地的总体思路

针对上述问题，我们最终把系统拆成了 4 层：

flowchart TD
    A[业务层
    对话UI / 可穿戴设备服务 / 视频场景] --> B[RTC会话编排层]

    B --> C[媒体控制层
    start / stop / update / push audio]
    B --> D[事件总线层
    ASR / 对话 / TTS / VAD / 工具调用]
    B --> E[上下文管理层
    角色 / 定位 / 设备 / 会话信息 / 工具权限]

    C --> F[底层RTC SDK]
    D --> G[实时消息通道]
    E --> G

    H[云端ASR / 对话服务 / TTS / Agent] --> F
    H --> G

    I[可穿戴设备 / 摄像头 / 本地文件] --> A

这 4 层的目标非常明确：

如果再往实现层落一层，这个“RTC 会话编排层”在代码里其实不是一个松散概念，而是一个单例协调器：

  • 对外暴露统一入口：初始化、启动、停止、更新、事件回调；
  • 对内维护会话状态：是否已启动、是否已建连、当前 channelId、当前 topicId；
  • 用不同队列处理不同问题：串行队列做状态收口，并发队列做事件分发；
  • 把底层 SDK、实时消息通道、业务上下文更新都收拢到一个类里。

这一点很重要，因为它决定了后续所有业务——无论是 App 内对话、外设语音、还是视频预览——都不会直接去碰底层 RTC SDK，而是统一经过这一层编排。

从实际工程实现看，这层编排的真实职责可以直接对应到几组方法：

  • 初始化入口：initializeRtcSDK()
  • 两种启动入口：startRtcEngine(...)、startRtcEngineWithBusiness(...)
  • 会中更新：updateAudioEnable(...)、updateFacingState(...)、updatePhotoInfoDuringRTC(...)
  • 业务上行数据：pushAudioData(data:)
  • 工具结果回传：pushMessage(mcpResponse:)
  • 统一事件入口：onEventMsg(_:)

也就是说，这个层并不是“理念上的中间层”，而是实打实地把启动、收流、发流、发配置、收事件、发工具结果全部收口到了一个类里。

1. 业务层只表达意图，不碰底层细节

业务层只做这些事：

  • 我要开始会话；
  • 我要停止会话；
  • 我要静音/取消静音；
  • 我要切换前后摄；
  • 我收到了 ASR / 回复 / 错误 / 工具请求后怎么更新业务状态。

这个说法并不是抽象结论，而是可以直接对上具体代码：

  • 4O 对话 ViewModel 只负责 setRTCConfigInfo(...)、startJoinRtcChannel()、startRtcEngine()；
  • 眼镜服务只负责在 handleStreamStart() 时把 delegate 切到自己、在录音回调里喂音频、在 rtcOnhandleAudioEvent(...) 里把下行音频送回设备；
  • 视频 ViewModel 只负责 startRtcEngine(with:)、updateRtcEngine(to:)、stopRtcEngine()。

业务层没有直接去调底层 RtcChatEngine.shared().start(...)，这说明现在的结构已经把 SDK 细节隔离得比较彻底了。

2. RTC 会话编排层统一管理生命周期

它负责：

  • 初始化底层 SDK；
  • 判断当前是否可启动；
  • 构建启动请求；
  • 管理 channel 状态；
  • 统一处理 stop、error、disconnect；
  • 将底层复杂事件转成业务可理解的回调。

3. 事件总线层承载“媒体以外的一切实时事件”

这里最重要的思想是：

RTC 会话里除了音频，还有大量强实时的控制消息和 AI 消息。

因此系统里会单独抽象一层事件总线，负责承载：

  • ASR 结果；
  • 对话回复；
  • TTS 状态；
  • VAD 状态；
  • 打断、拒识、拍照、结束事件；
  • 工具调用请求与工具结果回传。

4. 上下文管理层让会话“持续带脑子”

一次会话启动时会带一份基础上下文；
会话建立后，又能把新上下文增量更新进去。

这能保证系统不是“每轮问答都像全新开始”，而是始终在同一个实时上下文里运行。

四、为什么要设计成“双采播模式”

这是整套架构里最关键的一点。

在实际项目中，我们最后没有坚持“一种模式打天下”，而是明确拆成了两种采播模式。

而且这种区分不是停留在文档层面，而是直接体现在代码枚举上：

启动入口也明确拆成了两套：

  • startRtcEngine(...)：走 SDK 自采自播；
  • startRtcEngineWithBusiness(...)：走业务自采自播。

也就是说，采播模式从一开始就不是“某个配置项顺手改一下”，而是会影响整条启动请求、音频格式、设备信息以及会话开启原因。

1. 自采自播模式：适合 App 内对话

特点是：

  • 采集由 SDK 完成；
  • 播放也由 SDK 或 App 内链路完成；
  • 业务层主要关注 UI、状态和角色配置；
  • 接入成本低，适合语音助手、陪伴式对话等场景。

这类模式的优势是简单、稳定、延迟链路短。

在实际实现里，这一路对应的就是 4O 对话和视频场景：

  • 4O 对话走的是 rtcManager.startRtcEngine(topicId: topicId, enableAudio: !isMute, previewWindow: nil)；
  • 视频场景也是 startRtcEngine(...)，只是在外层额外接了前后摄切换 updateFacingState(...)。

这说明在这两个场景里，RTC 更多承担的是“App 自己发起一轮实时会话”的职责，而不是“替外设搬运音频”。

2. 业务自采自播模式：适合外设接入

当上行音频来自可穿戴设备，下行音频还要回放到外设时，媒体控制权必须握在业务层手里。

此时需要：

  • 业务侧主动推送音频帧到 RTC；
  • 业务侧接收 RTC 下发的音频帧；
  • 根据业务事件决定是否清空外设播放缓存；
  • 根据设备能力调整编码格式、拉流间隔和缓冲策略。

这类模式更复杂，但它是外设场景成立的前提。

在实际实现里，这一路就是眼镜语音链路：

  • 眼镜流服务拿到录音数据；
  • 建连前先缓存；
  • rtcDidConnect() 后逐包补发；
  • 后续持续调用 pushAudioData(data:) 上行；
  • 下行则通过 rtcOnhandleAudioEvent(audioData:clearBuffer:) 回给眼镜。

所以“business 模式”并不是为了抽象而抽象，而是专门为眼镜这种外设链路准备的。

3. 这不是“实现偏好”，而是架构边界问题

很多项目一开始试图把外设场景也硬塞进自采自播模式，后面通常都会遇到这些问题：

  • 无法精细控制上行数据节奏；
  • 无法可靠处理连接前缓存；
  • 打断播报时无法即时清理设备端 buffer；
  • 无法做精确的端到端时延观测。

所以更合理的结论是：

采播模式应该跟设备形态绑定，而不是跟 SDK 能力绑定。

五、RTC 生命周期应该怎么设计

如果把这套系统抽象成状态机，我更推荐这样理解：

stateDiagram-v2
    [*] --> Uninitialized
    Uninitialized --> Initializing
    Initializing --> Ready
    Initializing --> InitFailed
    Ready --> Starting
    Starting --> Connected
    Starting --> StartFailed
    Connected --> Updating
    Updating --> Connected
    Connected --> Stopping
    StartFailed --> Ready
    Connected --> Disconnected
    Disconnected --> Ready
    Stopping --> Ready

这里有几个实践经验很重要。

  • isRtcChannelConnected：底层 channel 是否建立；
  • rtcChannelId：当前会话 channel 标识；
  • currentTopicId：当前业务 topic；
  • rtcEnableAudio：当前拾音开关。

其中 rtcChannelId 甚至不是普通变量，而是放在专门的串行队列里保护读写，这一点很“工程化”，也非常实际：

这说明真实问题不是“我知不知道 channelId 是啥”，而是高频事件回调、会中更新、RTM 回传同时发生时，状态会不会乱。

这组状态在不同业务里分别对应不同问题：

  • 4O 对话更关心 initSDKState，因为它会在 startJoinRtcChannel() 里根据初始化状态决定是否立即 start；
  • 眼镜场景更关心 hasStartRtc 和 isRtcChannelConnected，因为这直接决定录音数据该缓存还是该实时上行；
  • MCP 结果回传和配置更新更依赖 rtcChannelId，因为 RTM publish 要绑到当前 channel 上。

1. 初始化状态和会话状态一定要分开

很多系统喜欢只维护一个 isConnected，这远远不够。

至少要拆成两类状态：

  • SDK 初始化状态：未初始化、初始化中、初始化成功、初始化失败；
  • RTC 会话状态：未开始、启动中、已连接、断开中、已断开。

两类状态混在一起，后面排查“为什么没连上”会非常痛苦。

2. 启动前先做一次前置校验

启动 RTC 前建议统一完成：

  • 鉴权 token 获取；
  • 当前场景配置准备；
  • topic/session/request 标识生成；
  • 当前是否已有会话在运行的检查；
  • 本次会话的音频模式、设备模式确认。

否则业务层每个入口都会各自补一遍校验，很快就失控。

  2. 如果 SDK 还没 ready，就直接返回，等待初始化完成后的 delegate 再重入启动；
  3. 会话真正 start 之前，会先统一重置 topic、channel、延时统计、音频开关等运行态。

这段逻辑和业务层的配合关系也很直接：

  • 4O 对话里，如果 SDK 已初始化，就直接 startRtcEngine()；
  • 如果没初始化，就只调 initializeRtcSDK()，真正 start 放到 rtcDidInitSuccess() 里继续；
  • 眼镜侧也是同样的思路：先在 handleStreamStart() 里 init，成功后由 rtcDidInitSuccess() 继续 startRtcEngineWithBusiness(...)。

这说明当前 RTC 的启动机制，本质上是一个“业务请求启动 -> 编排层做前置检查 -> SDK ready 后再真正进入会话”的两阶段流程。

3. stop 必须是幂等的

在真实环境里，stop 可能来源于：

  • 用户主动退出；
  • 错误回调；
  • channel 断开；
  • 页面销毁；
  • 外设主动结束录音；
  • 会话超时。

所以 stop 的设计必须天然支持重复调用、乱序调用和异步回调晚到。

六、真正的核心：启动请求里不能只有“媒体参数”

很多人第一次做 RTC，会把启动请求理解成：

  • 房间号；
  • 用户 ID；
  • 麦克风开关；
  • 摄像头开关。

但在智能交互场景里，启动请求实际上要承载三类信息：

1. 会话元数据

例如：

  • topicId / sessionId / recordId；
  • 用户身份；
  • App 版本；
  • 设备类型；
  • 当前终端能力。

它解决的是“这一轮实时交互到底是谁、在什么设备上、以什么身份发起”的问题。

2. 智能体配置

例如：

  • 角色设定；
  • 历史记忆开关；
  • 是否开启多模态；
  • 是否允许工具调用；
  • 是否允许控制外设或车辆；
  • 是否开启推送通知或延迟补偿策略。

它解决的是“这次会话里，智能体应该以什么能力工作”的问题。

3. 语音交互配置

例如：

  • VAD 策略；
  • ASR 配置；
  • TTS 参数；
  • 上下行音频格式；
  • 弱网补偿和 buffer 策略。

它解决的是“实时交互这件事，要用什么声音策略去完成”的问题。

当这三类配置都统一由 RTC 编排层构建时，业务接入会非常清晰；
反之，如果散落在 UI 层、设备层、服务层多个地方，系统会快速失去一致性。

在实际代码里，启动请求确实就是这样拼出来的。它不是把几个字段塞进 SDK 就结束，而是按顺序组装：

如果是 App 内对话模式，还会继续补：

  • startReason = userClick；
  • 不携带 wearable device。

如果是外设语音模式，则会改成：

放到实际业务代码里，这个“会话画像”至少包含三层业务语义：

  1. 当前是谁在发起会话

    • 账号、设备、App 信息；
    • 眼镜场景还会额外注入 wearable device。

  2. 当前这轮会话要以什么方式运行

    • 4O 对话会带角色配置、首次进入标记、是否角色切换；
    • 眼镜场景会带更强的多模态和设备控制配置。

  3. 当前会话要开放哪些实时能力

    • 语音识别；
    • 对话回复；
    • 打招呼；
    • MCP 工具；
    • 拍照相关上下文。

所以这套 RTC 的启动请求，本质上已经不是“房间参数”，而是“一轮 AI 会话的运行时描述”。

七、把 RTC 当作“事件总线”，系统会豁然开朗

这是本文最想强调的一个观点。

1. 媒体流只是总线中的一部分

一条会话里真正流动的，不只有音频帧，还有：

  • ASR 文本；
  • 对话结果；
  • TTS 播放状态；
  • 说话开始/结束事件；
  • 打断事件；
  • 拍照事件；
  • 表情状态；
  • 工具调用请求；
  • 工具调用结果。

如果把这些都视为“附属逻辑”，系统会变成一堆横向打补丁。

更好的做法是：

把 RTC 会话看成一条实时事件总线，媒体流只是其中一种消息。

2. 用统一消息封装做事件扩展

在工程实现上，比较推荐的做法是使用统一的 envelope：

  • 一个标准消息头；
  • 一个 type 字段；
  • 一个 payload；
  • payload 内部再按具体类型解码。

这样做有三个直接收益：

  1. 新事件类型扩展成本低；
  2. 业务层不直接依赖底层传输细节；
  3. 云端和端侧可以基于同一套消息协议演进。

3. 事件要继续被抽象，而不是原样抛给业务

底层协议再丰富，也不应该让业务直接消费“底层结构”。

业务真正需要的通常只是：

  • 识别开始/结束；
  • 播报开始/结束；
  • 当前这轮是否拒识；
  • 是否触发拍照；
  • 是否收到工具调用；
  • 当前回复是否结束。

因此编排层最好再提供一层统一事件接口，把底层复杂度屏蔽掉。

这一点在实际代码里也非常清楚。对外暴露的 delegate 不是底层 SDK 原始回调，而是一组业务语义更强的接口：

  • chatEvent

  • channelEvent
  • errorEvent
  • networkQualityEvent
  • rtcStatsEvent
  • agentStatsEvent

这些事件先在统一入口里分流，再在 chatEvent.data_p 里继续解出：

  • ASR 响应；
  • 对话响应；
  • MCP 请求；
  • 其它事件数据。

实现上用的是 GPBAny + TypeURL + serializedData 这一套，这意味着你拿到的并不是“固定字段对象”，而是一条真正可扩展的 protobuf 消息总线。

而这些事件在不同业务里分别落到了不同地方：

  • 4O 对话只关心 rtcOnAsrEvent、rtcOnChatEvent、rtcDidConnect，用来驱动 UI 状态和建连耗时统计；
  • 眼镜场景除了关心 ASR/回复，还要消费 rtcOnhandleAudioEvent、rtcChatEventType、rtcOnMcpRequestReceived，因为它还要处理 TTS 下发、打断、拍照、结束、工具执行；
  • 视频场景则主要关注 rtcDidConnect、rtcDidDisconnect 和摄像头状态切换。

这也解释了为什么同一个 RTC 管理器可以同时服务多个业务：底层事件源是统一的，但每个业务只消费自己需要的那部分语义事件。

八、可穿戴设备接入时，音频链路要重点解决什么

可穿戴设备场景最容易被低估。

表面看只是“设备采音，手机转发”，实际上至少要解决四个工程问题。

1. 连接建立前的数据不能丢

用户被唤醒后，往往会立刻说第一句话。

但这时候 RTC 连接未必已经建立完成。若没有预缓存机制，就会丢掉最关键的首包语音，表现为：

  • 首词缺失；
  • 识别不完整；
  • 用户感觉“设备听不见我”。

正确做法是：

  • 在 RTC 建连前缓存音频数据；
  • 建连成功后按原始包粒度补发；
  • 缓存上限可控，避免异常情况下 OOM。

2. 打断时必须能清空播放缓冲

在语音助手场景里，打断是高频动作。

如果只是本地停止播放，而外设端还积压着上一轮 TTS buffer，用户会听到明显的“残音”。

因此下行音频事件里最好携带一个明确的 clearBuffer 语义，业务层收到后立刻通知外设清空缓冲区。

3. 端到端时延要拆段观测

只测“RTC 延迟”远远不够，真正影响体验的是：

  • 外设采音到 App；
  • App 到 RTC；
  • VAD 结束到 TTS 开始；
  • RTC 到 App；
  • App 到外设播放。

如果不拆段，只看一个总耗时，你很难知道瓶颈到底在网络、云端推理、App 转发，还是设备播放。

4. 参数要跟设备唤醒信息联动

外设通常会在唤醒时带一些附加信息，比如：

  • 建议的 burst buffer 大小；
  • 是否需要回声回灌；
  • 当前设备状态；
  • 最近一次拍照或传感器信息。

这些参数不应该散落在业务层，而应该在会话启动时被统一吸收进上下文里。

九、会话不是一次性请求，而是“持续更新的上下文容器”

这是智能交互场景与传统通话场景的另一个核心差别。

1. 启动时带上下文，只是第一步

一个会话刚建立时，系统一般会带上：

  • 用户信息；
  • 设备信息；
  • 角色配置；
  • 初始能力开关；
  • 初始位置与终端状态。

但这些信息不是一成不变的。

2. 会中上下文更新才是体验关键

例如：

  • 连接建立后先上报缓存定位，再异步刷新真定位；
  • 用户切换设备或车辆上下文时，需要同步到会话；
  • 用户刚拍完照片，图像信息要尽快进入本轮对话；
  • 工具权限或能力开关可能在会话中发生变化。

所以 RTC 架构里最好内建一条“会中上下文更新通道”，而不是每个业务单独开旁路接口。

3. 为什么建议用增量更新，而不是全量重建

因为全量重建会带来：

  • 带宽浪费；
  • 协议冗长；
  • 覆盖错误风险；
  • 新老字段演进困难。

增量更新更适合实时会话：

  • 谁变化就更新谁；
  • 谁感知强就优先推谁；
  • 编排层负责合并与兜底。

十、一个典型案例：语音唤醒后的“拍照记”如何串起整条链路

前面讲了很多架构原则，如果只停留在抽象层面，读起来很容易觉得“概念都对，但离真实业务还有点远”。

下面用一个非常典型的场景，把前面的几个关键设计点串起来：

用户先在眼镜上拍了一张照片，随后再次语音唤醒助手，说“帮我记一下刚刚拍的那张照片”。

这个场景看似只是一次“语音记事”，但它实际上同时依赖了：

  • 外设唤醒数据透传；
  • RTC 启动前上下文注入；
  • 工具注册与工具调用；
  • 端侧执行回写；
  • 图片同步完成后的本地后处理。

如果缺少其中任何一环，最终体验都会断掉。

1. 第一步：拍照动作本身，和后续对话是两段链路

这个场景里有一个很容易被忽略的事实：

  • 用户拍照时，完成的是一次“拍照动作”；
  • 用户随后说“记一下刚刚那张照片”时，开启的是一次新的“语音会话”。

也就是说，“拍照”与“对话”并不是同一个 RTC 会话内的连续动作，而是两段先后发生、需要靠上下文重新关联起来的链路。

这也是为什么，系统不能只依赖“当前会话状态”，而必须有能力把 上一个动作产生的关键上下文，带进下一次语音会话里。

2. 第二步：在唤醒瞬间，把 photo_id 带进 App

当用户再次唤醒助手时，眼镜侧会在唤醒数据里把最近一次拍照的 photo_id 一并带上来。

  • 用户先拍照；
  • 设备记住这张照片的 photo_id；
  • 下一次唤醒时，把这份上下文带给 App；
  • App 把它暂存在一个会话外可访问的位置。

这一步解决的是：

下一轮 AI 会话，怎么知道用户口中的“刚刚那张照片”具体是哪一张。

3. 第三步：在 RTC 启动前，把拍照上下文注入对话配置

仅仅把 photo_id 存在本地还不够，云端智能体必须在本轮会话开始时就能感知到它。

这里有两个非常重要的设计点：

其一：这是“启动前注入”，不是“识别后补发”

也就是说，智能体在理解用户第一句话时，就已经拿到了“最近一次拍照”的上下文，而不是等识别完成后，再由端侧追加一条补充信息。

这会直接影响首轮理解质量。

其二：传的不只是 photo_id，还有时间信息

除了 photo_id，系统还会把唤醒时间、建连时间等信息一起上报。这样远端就能做更稳妥的判断，例如：

  • 这张图片是不是刚刚拍的；
  • 当前请求说的“刚刚那张”是否仍在合理时间窗口内；
  • 是否应该自动触发“拍照记”工具，而不是误把一张旧图当成本轮目标。

从工程角度看，这体现出一个很重要的经验：

上下文不要只传“对象 ID”，还要传“时间语义”。

  6. 如果本地文件已可用，再继续执行上传；
  7. 上传成功后更新附件状态与远端地址，并通知 UI 刷新。

这是一条非常典型的“实时决策先完成语义绑定，离线后处理再补完资源绑定”的链路。

这个案例很能说明一件事：

RTC 的价值，不只是让用户“说上去、听下来”，而是把设备上下文、智能体理解、工具执行和资源后处理组织成一条完整的实时业务链路。

十一、为什么说“工具调用”会改变 RTC 的角色

一旦系统支持 Agent 工具调用，RTC 的职责会立刻发生变化。

因为此时会话链路不再只是：

用户说话 -> 云端回复 -> 语音播报

而会变成：

用户说话 -> 云端理解意图 -> 云端发起工具请求 -> 端侧执行工具 -> 工具结果回传 -> 云端继续生成回复 -> 语音播报

这条链路里，工具请求和工具结果同样具备强实时性。

因此 RTC 或与之配套的实时消息通道，天然适合承担两件事：

  1. 云端向端侧下发工具调用请求；
  2. 端侧将执行结果与当前会话绑定后回传。

从架构视角看，这意味着：

RTC 不再只是“传声音”，而是开始承载智能体执行闭环。

这也是为什么未来很多“实时语音助手”系统，本质上会越来越像“实时 Agent Runtime”。

十二、可观测性必须从第一天就设计进去

这类系统上线后，最常被问到的问题不是“有没有 bug”，而是：

  • 为什么这次连接慢？
  • 为什么刚才听不见？
  • 为什么识别慢了 1 秒？
  • 为什么设备端播报卡顿？
  • 为什么用户感觉打断不生效？

这些问题如果没有可观测性，几乎无法复盘。

我比较推荐至少做四类指标。

1. 生命周期指标

  • 初始化成功率；
  • 启动成功率；
  • 会话断开原因分布；
  • 更新请求成功率。

2. 时延指标

  • 建连耗时；
  • VAD 结束到 TTS 开始耗时；
  • 音频回包间隔；
  • 端侧转发到外设的耗时。

3. 环境指标

  • 当前前后台状态；
  • 当前网络状态；
  • 当前设备形态；
  • 当前场景类型。

4. 事件指标

  • 打断次数；
  • 拒识次数；
  • 拍照触发次数；
  • 工具调用成功率；
  • 工具结果回传成功率。

注意，这些指标不是“附加价值”，而是实时智能交互系统真正稳定运行的基础设施。

十三、这套架构最值得复用的 6 个设计原则

总结下来，我认为最值得复用的是下面 6 条。

1. 用一个会话编排层收口所有入口

不要让 UI、设备服务、视频模块分别直接操作 RTC SDK。

2. 把“初始化状态”和“会话状态”拆开管理

这是处理异步和排障的前提。

3. 同时支持自采自播和业务自采自播

设备形态不同，媒体控制边界就不同。

4. 把 RTC 看成“媒体 + 事件 + 上下文”的组合体

只有这样，系统才能平滑承载 AI 场景。

5. 会中上下文更新必须是一等公民

定位、设备、图片、权限、角色都应该支持增量更新。

6. 可观测性要覆盖端到端链路

不是只看 SDK 日志，而是看完整的用户感知路径。

十四、有哪些容易踩的坑

最后也补几个很常见的坑。

1. 单例很方便，但要警惕多场景竞争

如果所有业务都共用一个全局 RTC 管理器，要特别注意：

  • 当前 delegate 属于谁；
  • 页面销毁后是否正确释放；
  • 新场景进入时是否打断旧场景。

2. 业务层不要直接依赖底层协议结构

否则协议一变，所有业务都会被连带修改。

3. 缓冲区一定要有上限

连接前缓存是必须的，但无上限缓存一定会埋下内存风险。

4. stop 和 error 的时序要允许“重复、乱序、晚到”

异步系统里，这不是异常，而是常态。

5. 上下文更新要防止旧值覆盖新值

尤其是在定位、图片、设备状态这类高频变化信息上。

十五、结语：RTC 正在从“通话能力”演进为“实时智能交互底座”

如果只把 RTC 当成实时音视频能力，你得到的通常只是一个“能通”的系统。

但如果把它放到语音助手、可穿戴设备、多模态输入、工具调用这些真实业务里看，RTC 更适合被理解为：

一个承载媒体流、事件流、上下文流与执行流的实时智能交互底座。

它连接的不只是人和人，或者端和端；
它连接的是：

  • 用户输入；
  • 设备能力；
  • 云端智能体；
  • 外部工具；
  • 持续变化的会话上下文。

从这个角度看，真正有价值的 RTC 架构，不是把 SDK 接起来，而是把“实时交互系统”组织起来。

而当一套系统已经能同时处理媒体、状态、事件、上下文和工具执行时，它其实已经不再是传统意义上的 RTC 模块，而是一套面向实时 AI 的运行时基础设施。
