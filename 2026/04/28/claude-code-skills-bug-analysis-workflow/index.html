用 Skills 打通 Bug 分析流水线：5 个 Skill 的设计与串联

PUBLISHED 2026.04.28
AI Coding Claude Code Skills Bug分析 工程实践

从一个反直觉的设计说起

Skill本质上就是一个放在 ~/.claude/skills/<name>/SKILL.md 或者~/.codex/skills/<name>/SKILL.md 里的 Markdown 文件。没有特殊 API，没有插件机制，加载后直接注入进 system prompt。

这听起来挺简陋的。但实际用下来，发现它反而是最合适的抽象方式.因为真正让 AI 变强的不是给它更多工具，而是给它”领域知识”：这个系统的坑在哪、字段含义是什么、什么情况下该停下来问人。这些东西写成自然语言比写成代码更容易维护。

目前团队内使用的 Bug 分析体系有 5 个相互依赖的 Skills，下面从实现层面把它们拆开讲。

两种 Bug 来源，两条完全不同的链路

先把场景说清楚，因为这决定了整个架构。

第一种：公司内部测试人员在 JIRA 上提的 Bug。 测试同学测出问题，手动创建 JIRA Issue，把日志压缩包、截图、视频作为附件上传上去。日志存在 JIRA 附件里，鉴权靠 JIRA 的 Personal Access Token。

第二种：真实用户通过 App 的意见反馈功能主动上报。 用户在 App 里点”意见反馈”，App 自动打包当时的系统日志一起上传。这份日志不走 JIRA，走的是另一套内部平台——AISP Community CMS，日志文件存在百度 BOS 上。

两个来源，两套鉴权，两种定位方式。对应两条链路：

Skill 1：ois-download — 有 OIS 鉴权能力的 BOS 下载工具

这个 Skill 干的事很直接：给一个 fileKey，把文件从百度 BOS 下回来。日志压缩包、截图、任何存在 BOS 上的文件都能用它下。

复杂的地方不在下载本身，而在鉴权。BOS 是私有存储，不能直接访问，必须先拿到合法凭证才能下载。这个 Skill 通过 OIS 解决了鉴权问题，所以叫”有 OIS 鉴权能力的 BOS 下载工具”。

OIS（Object Integrated Storage）是公司内部云服务部门提供的对象存储接入服务，统一封装了百度云、阿里云、火山云等公有云的对象存储，对外提供统一的访问入口。使用方有两条路：一是直接用 OIS 的 SDK；二是调 OIS 的 HTTP 接口拿临时 AK/SK（Access Key / Secret Key，即临时访问密钥对），再用各家公有云的原生 SDK 操作。

这个 Skill 走的是第二条路：给你一个 fileKey，通过 OIS 接口拿到访问百度 BOS 的临时凭证，再用百度云原生 SDK 生成预签名 URL 完成下载。正因为用到了百度云 SDK，首次使用前需要先安装依赖：

Skill 里的 check_dependencies.sh 会自动检测并安装，但如果网络受限或环境有问题，也可以手动跑这一步。

看起来很简单，实际上绕了好几道弯。

为什么不能直接 curl

日志文件存在百度 BOS 的私有 bucket 里，直接访问需要鉴权。正常的做法是维护一个长期 Access Key，但这有两个问题：一是 Key 一旦泄露影响面很大；二是不同角色的人对文件的访问权限应该不同，用一把长期 Key 很难做细粒度控制。

所以这里走 OIS 的 STS 临时授权方案：不持有任何长期凭证，每次下载时现去 OIS 申请一组只有 3600 秒有效期的临时 AK/SK + SecurityToken，用它生成一个带签名的一次性下载 URL，下完即过期。整个过程 Skill 本地不存任何 secret，权限控制交给 OIS 统一管理。

这套流程背后还有一个好处：因为走了 OIS 这层统一入口，底层换成阿里云或火山云对上层完全透明，Skill 代码不需要改。

SIADA MCP 的协议细节

OIS 申请 STS 凭证的接口不是普通的 REST API，而是通过 SIADA MCP 服务暴露的——这是公司内部 AI 平台统一对外提供工具调用的方式，接口协议遵循 MCP（Model Context Protocol）标准。所以 Skill 脚本里不是简单地 curl 一个 REST 接口，而是要按 MCP 协议走完整的会话流程。

具体有一个容易踩坑的地方：每次调用前必须先发一个 initialize 握手请求，然后才能发 tools/call，两个请求打到同一个 endpoint。

返回的 JSON 是两层嵌套的：外层是 MCP 协议层（result.content[0].text），里面才是真正的业务 JSON。解析时要先取 .result.content[0].text，再对这个字符串做第二次 jq 解析，才能拿到 accessKeyId、accessKeySecret、securityToken。

拿到 STS 凭证之后，交给 Python 的 baidubce SDK 生成预签名 URL。这里有个隐蔽的坑：baidubce 的 generate_pre_signed_url 返回的是 bytes 类型，不是 str，如果直接打印会得到 b'https://...' 这样带前缀的字符串。generate_url.py 里做了显式的 decode：

Skill 2：lisa-query-feedback — 从用户 accountId 找到日志的 fileKey

这个 Skill 干的事只有一件：给一个用户 accountId，查出他在 App 里提交的所有意见反馈记录，每条记录里有 fileKey，指向 BOS 上对应的日志文件。

为什么需要单独一个 Skill 做这件事？因为用户上报的日志不在 JIRA 里，而是存在公司内部的意见反馈平台。开发者要分析用户反馈的问题，必须先来这里找到日志的 fileKey，才能交给 lisa-log-download 去下载。没有这一步，根本不知道日志在哪。

运作方式很简单：给一个 accountId，Skill 调内网的意见反馈平台接口，拉出这个用户提交的所有反馈记录，整理成表格输出——每条记录包含提交时间、App 版本、反馈内容摘要，以及最关键的 fileKey。拿到 fileKey 之后直接交给下一个 Skill 去下载日志。

Skill 3：lisa-log-download — 把日志下回来、解压好，准备供分析

这个 Skill 的定位是：拿到 fileKey 之后，把 BOS 上的日志文件下回来、解压、整理成可以直接读的目录结构。它是 ois-download 的上层封装，补充了两个 ois-download 没有的能力：一是”不知道 fileKey 时先查”，二是下载后自动解压处理。

为什么要单独抽这一层？因为实际使用中经常遇到”只知道用户 accountId，不知道具体哪个日志文件”的情况——lisa-query-feedback 拿到的是反馈记录，ois-download 只负责下载，中间的”查日志记录拿 fileKey”这步需要有人做，就是这个 Skill。

模式一：已知 fileKey，直接下载。 调 download-by-ois.sh，走 SIADA MCP → BOS 链路把文件拉回来，自动解压。

模式二：不知道 fileKey，先查。 调 query-logs.sh，走另一个 SIADA MCP 工具（tool ID 1823985084370276360，用 entityCode com.lixiang.crs.question.file.limate 做过滤），拿到日志记录列表，再从里面取 fileKey 去下载。

两个 SIADA MCP 工具 ID 不一样，但协议是一样的：initialize → tools/call → 解析两层 JSON。

比如一行日志在 868ms，最近的锚点是 10383ms → 00:54:20，那这行的时间就是 00:54:20 - (10383 - 868) / 1000 = 00:54:10.485。

分析跨端 Bug 时（App + 眼镜同时出问题），把两份日志的时间对齐是第一步，缺了这个换算公式就没法做。

Skill 4：jira-integration — JIRA 操作的统一基础层

这个 Skill 是其他所有需要访问 JIRA 的 Skill 的共同底座：统一管理凭证、提供标准化的 API 封装，让上层 Skill 直接拿来用，不用各自处理鉴权细节。

为什么要单独抽出来？如果每个 Skill 各自维护 JIRA 凭证和 API 调用逻辑，凭证分散在多处、API 用法也可能不一致。集中在一个地方，凭证只存 ~/.claude/settings.json 一份，API 用法有统一的参考模板，改一处全部生效。

用 PAT（Personal Access Token）而不是用户名密码，原因是现代 JIRA 推荐 Bearer Token 方式，Basic Auth 属于 legacy 方案，部分实例已经不支持。

Skill 5：jira-bug-analysis — 整条流水线的唯一入口

这是整个体系的编排层，也是开发者唯一需要直接打交道的 Skill：给一个 JIRA Key，它把前面所有 Skill 串起来，从拉取 Bug 信息、下载附件、分析日志，到生成结构化报告，全部自动完成。

为什么需要这一层？前面四个 Skill 各自解决一个具体问题，但 Bug 分析是一个有顺序依赖的多步流程，光有零件不够，还需要一个知道”先做什么、后做什么、什么时候该停下来问人”的编排者。这个 Skill 就是那个编排者。

完整执行流程

时间锚定这件事为什么重要

一份 Bug 日志里可能有几十条异常信号，如果每条都去追查，既慢又容易跑偏。”时间锚定根因分析法”的核心动作只有一个：排除掉窗口外的异常。

每个候选根因用一张表来做决策：

异常信号 最后发生时间 Bug 窗口内是否持续 能否解释现象 结论
蓝牙断连 14:23:17 ✅ ✅ 候选根因
内存告警 14:10:05 ❌ ✅ 排除（时间不重合）
RTC 超时 14:24:01 ✅ ❌ 排除（现象不匹配）

内存告警在 14:10 就结束了，问题发生在 14:23 窗口内，时间不重合，直接排除。不管它看起来多”可疑”。这个过滤步骤能把需要深查的候选项从几十个压到 2-3 个。

截图为什么优先于 occurrenceTime？因为截图上的系统时间是系统自动打的，用户填的 occurrenceTime 可能早、可能晚，尤其是用户过了几小时才提交反馈的时候，偏差可以到 ±30 分钟。

整体架构回顾

两条链路的核心差异：

链路 A（JIRA 内测） 链路 B（用户意见反馈）
Bug 来源 内部测试同学手动提交 真实用户 App 内上报
日志存放 JIRA 附件 百度 BOS
鉴权方式 JIRA PAT（长期凭证） SIADA MCP STS（临时，3600s）
入口 JIRA Key（LIG-xxxx） 用户 accountId
核心 Skill jira-bug-analysis lisa-query-feedback → lisa-log-download

真实效果

分析测试在Jira上提出的bug

  • 直接把jira issue id给到AI，会先规划拆分任务
  • 首先会识别到需要使用jira-bug-analysis这个skill
  • 接着会读取配置中的jira中的认证信息并获取bug信息
  • 接着会下载附件信息（日志文件、截图等），并解压
  • 拿到bug的所有信息后，开始分析
  • 分析完后会形成分析报告存储在本地
  • 用户进行选择

    这是拿之前解决的一个bug进行测试，分析的结果准确无误！

分析用户在APP提交的日志反馈

  • 请求查询指定用户id的反馈问题，会自动使用lisa-query-feedback这个skill，并按照skill内容进行操作
  • 给出用户反馈的问题
  • 要求下载日志进行分析，自动调用ois-download这个skill
  • 先检查BOS的依赖是否符合，自动解决
  • 然后进行鉴权处理
  • 预签名 URL 生成成功，下载日志进行解压
  • 分析日志
  • 最终给出分析报告

Skills 对 Bug 分析流程的意义

Bug 分析本质上是一个知识密集型的工作：要知道日志在哪、怎么鉴权拿到、不同平台的字段有什么坑、时间怎么对齐、根因怎么排查。以前这些知识分散在不同人脑子里，换个人来处理就得重新摸索一遍。

Skills 做的事，是把这些知识从个人脑子里搬到系统里。

流程可复用。 五个 Skills 组合成两条固定链路，任何人说出一个 JIRA Key 或者 accountId，就能跑起来完整的分析流程，不需要了解背后每一步怎么做。以前需要熟悉整套系统才能独立处理的工作，现在降低到了”知道入口”就够。

经验可沉淀。 眼镜日志时间戳要用 [UA] 锚点换算、JIRA 状态变更必须先查 transition ID 再执行——这类踩坑才知道的细节，写进 Skill 之后就变成了流程的一部分，不会因为换人处理而重复踩坑。

质量有保障。 jira-bug-analysis 里的强制人工确认节点，确保 AI 分析结果在发布到 JIRA 之前经过人工审核。这不是对 AI 能力的不信任，而是对”有副作用的操作”的边界划定——AI 负责分析，人负责决定要不要发出去。

这套体系真正解决的问题，是让 Bug 分析从”依赖个人经验”变成”依赖系统流程”。
