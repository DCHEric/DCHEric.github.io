iOS 端 MCP 协议网关的架构设计：从协议适配到多业务域路由

PUBLISHED 2026.04.08
AI Agent iOS MCP 架构设计 协议网关 任务调度

最近在做一个智能硬件 + AI Agent 的项目，其中有一块专门负责对接 AI 系统下发的 MCP（Model Context Protocol）请求，把它们路由到眼镜硬件控制、车辆控制、音乐播放、笔记记录等各个业务域。

这套模块做下来，积累了不少关于「协议网关在移动端落地」的思考，整理出来供大家参考。

MCP 协议基础

MCP 是什么

MCP（Model Context Protocol，模型上下文协议）是 Anthropic 于 2024 年 11 月发布的开放标准协议，目标是解决 AI 模型与外部工具、数据源之间「各说各话」的问题。

在 MCP 之前，每个 AI 产品对接外部能力都要自己定一套接口格式，工具和模型之间是 M×N 的定制集成；MCP 引入统一规范后，变成 M+N 的标准接入——工具只要实现 MCP，就能被任何支持 MCP 的模型调用。

三个核心角色

  • Host：用户直接使用的 AI 应用（如对话客户端），负责协调 LLM 和 MCP Client
  • Client：协议会话的发起方，维护与 Server 的 1:1 连接，代表 Host 向 Server 发送请求
  • Server：对外暴露工具能力的服务（可以是本地进程、远程服务，或者——如本文的场景——端侧 App 本身）

在端侧场景里，App 同时扮演 Host 和 Server 两个角色：一方面是用户的 AI 对话入口，另一方面向 AI 后端暴露「可以调用哪些本地能力」。

MCP 与 Function Calling 的区别

很多人会问：MCP 和 OpenAI 的 Function Calling 有什么区别？

维度 Function Calling MCP
定位 单一模型厂商的私有规范 跨厂商开放标准
工具发现 每次请求手动传入 tools/list 动态发现
连接模型 直连 API Client-Server 架构，可跨进程
状态 无状态 有状态会话（supports resources, prompts）
传输层 HTTP/SSE 可插拔（stdio、SSE、WebSocket 等）

简单说：Function Calling 是「模型能用工具」，MCP 是「模型和工具如何标准化对话」。

在端侧场景的变体

标准 MCP 假设 Server 运行在独立进程（本地 stdio 或远程 HTTP），但在移动端 AI 场景里，工具执行天然要在 App 进程内完成（调蓝牙、操本地 DB、控 SDK）。因此端侧实现会做几处适配：

  1. 传输层替换：用 RTC/gRPC 替代 stdio/HTTP，消息格式保持 JSON-RPC 语义
  2. 工具声明时机：不是 tools/list 请求时才发，而是随对话初始化配置一次性下发
  3. Server 内嵌 App：App 本身就是 MCP Server，工具调用直接驱动本地能力

这三处适配，是理解本文整套架构设计的前提。

背景：为什么需要 MCP 协议网关

有了 MCP 协议，AI 和工具之间的通信有了统一标准。但在端侧落地时，马上面临一个新问题：AI 侧是统一协议，端侧的业务却天然是分散的——眼镜走 BLE 蓝牙、车控走私有协议、音乐调第三方 SDK、笔记走镜控拍照。

把一个统一协议请求，正确路由到多个异构业务域，再把结果统一封装回去——这就是这个模块要解决的核心问题。

一、模块整体职责

这个模块可以理解为一个 MCP 协议执行中枢，主要分两块：

1. Tool 元数据管理（ToolManager）

负责维护 MCP tool list，向上游声明「当前 App 和眼镜支持哪些工具、每个工具的参数格式是什么」。

2. 任务调度与执行（TaskManager + Executor）

负责把 MCP 请求转成任务对象、选择执行器、排队执行、生成响应并发回上游。

二、核心分层架构

从职责来看，整个模块分成四层。

第 1 层：协议层

文件：MCPModels.swift

负责解析和封装 MCP 传输数据。

上游通过 protobuf 传入 MCPRequestTransportData，协议层把它解包为内部模型 MCPRequest。关键在于：原始数据里的 content 字段是一段 JSON-RPC 字节流，需要再次解析才能拿到 methodName 和 arguments。

这里有一个值得注意的设计：MCPResponse 提供了 success / failure 两个静态工厂方法，失败响应会自动生成符合 JSON-RPC 规范的 error 结构，业务层不需要关心协议格式。

第 2 层：调度层

文件：AITaskManager.swift

负责任务生命周期管理。

调度层是整个模块的「大脑」，核心逻辑集中在 receiveMCPRequest → executeNextTask → handleTaskResult 这条主干上。所有操作都派发到 taskQueue（一个串行 DispatchQueue），保证任务数组的线程安全。

串行消费模型：executeNextTask 每次只取第一个 waiting 状态的任务执行，上一个任务的 handleTaskResult 回调里再触发下一个。这对顺序保证很好，但如果某个任务长时间阻塞（比如眼镜拍照超时），后续任务全部等待。

串行模型的固有约束：任务生命周期完全依赖执行器的 completion 回调。如果某个执行器因为底层 SDK 无响应、BLE 断连等原因迟迟不回调，这个任务就会长期占据队列头部，后续任务全部等待。因此每个 AITask 预留了 timeoutInterval 字段（默认 20 秒），超时保护是这套串行模型的必要配套，在硬件联动类业务场景里尤为关键。

第 3 层：执行层

文件：AITaskExecutor.swift + 各业务 Extension

负责按业务路由，驱动实际能力。

路由规则：source（请求来源APP还是眼镜）一级分流 + methodName （具体的指令操作）二级路由。

业务逻辑通过 Swift Extension 按域拆分到独立文件，主执行器本身只做路由转发：

第 4 层：能力描述层

文件：MCPToolManager.swift

负责向外声明支持的工具集。

它不执行业务，只提供 JSON Schema 形式的工具元数据，告诉 AI「你可以调哪些工具、参数格式是什么」。App 工具集固定在本地 app_function_list.json 里，以 MD5 作为版本标识，实现很简洁。

针对智能眼镜，做了一套动态能力协商机制：低版本固件使用本地内置工具集，高版本固件通过 CRC 校验 + 多级缓存（内存 → 沙盒 → 服务端拉取 → 本地回退）动态获取最新工具集。

工具集并不是通过独立接口注册给 AI 的，而是在发起 AI 对话时，作为对话配置的一部分一起下发。

  3. 通过 BLE 把命令转发给眼镜执行

这种「能力边界」设计值得借鉴——工具本身不做模糊推断，把歧义还给 AI 去处理，AI 再通过对话澄清。这符合 MCP 工具的设计哲学：工具要么成功执行，要么返回明确的错误类型，不做「聪明的猜测」。

通用镜控（音量、录音、相机等）是透传模式：直接把 JSON-RPC 的 params 序列化后下发眼镜，眼镜侧处理并返回字符串结果，App 侧直接透传。这种设计灵活、统一，代价是 App 侧缺少参数校验，协议稳定性强依赖硬件固件端。

B. 车控：长事务的多阶段回包设计

车控是整个模块里设计最特殊的业务域，因为它是一个长事务。

发出「关闭车窗」命令后，不是立刻返回最终结果，而是：

  1. 先获得一个 jobId（任务单号）
  2. 通过主回调返回「命令已下发」的初始响应（MCP 层面任务完成）
  3. 通过独立的上报回调持续接收状态更新（执行中/执行完成/执行失败）

D. 笔记业务：双写补偿策略

笔记记录（ov_note_write）的核心挑战在于：眼镜侧的状态和 App 本地数据侧的状态需要保持一致，但这两个写入是异步的、可能局部失败的。

策略是：

  • 主路径：下发命令让眼镜记录 note_id（写入眼镜端）
  • 补偿路径：无论眼镜回调成功还是失败，只要本地有对应的图库资源，就在 App 侧做补偿写入（创建笔记、挂载附件）

这是一种双写补偿策略：眼镜侧写入为主，App 本地做兜底一致性保证。这在「设备端 + 云端」协作的场景里很常见，比分布式系统里的 Saga 模式轻量很多，但核心思路一致——局部失败不影响整体最终一致。

七、响应构造的双向适配器模式

整个请求执行流程里有两次分发：

这是一种双向适配器（Bidirectional Adapter） 设计——进来的时候统一解包，出去的时候按类型重新封装。

响应构造器集中在 JSONRPCParser 里，提供各类 builder 方法：

  • 图片响应（含 URL、MIME 类型、尺寸）
  • 通用硬件控制响应（透传硬件返回的 param dict）
  • 车控响应（包装 SDK 返回的 data 字段）
  • 切换设备响应
  • 权限查询响应
  • 笔记写入响应
  • 音乐搜索响应
  • 失败响应（标准 JSON-RPC error 结构）

集中封装的好处是：业务层只需要关心返回什么数据，不必自己拼完整的 JSON-RPC 协议壳。

八、一句话总结

这套模块是 iOS 端面向 AI 系统的 MCP 协议执行中枢，负责能力声明、请求解析、任务调度、业务路由、结果回包，以及语音会话退出策略的联动。

通俗讲：「AI 发命令 → App 执行 → 按 MCP 协议把结果回给 AI」的总中台。

这类「协议网关 + 多业务路由」的架构模式，不只出现在 AI Agent 场景里。凡是需要在移动端把一个统一上游协议分发到多个异构业务域的场景，都可以借鉴这套分层思路：协议层负责解析封装、调度层负责生命周期、执行层按域拆分、能力描述层对外声明。

核心要点是保持层间的职责边界清晰——一旦某一层开始承担太多职责（比如执行器既路由又存状态又控 UI），整体可维护性就会快速下降。这是所有「网关类」架构最容易踩的坑，也是从这套实现里最值得带走的教训。
