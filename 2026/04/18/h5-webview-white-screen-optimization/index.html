一、WebView 渲染流程

整个流程由 WebKit 框架驱动，运行在 iOS 系统的 WebContent 沙盒进程中。

① 初始化 WKWebView

iOS 8 之后，苹果用 WKWebView 取代了老旧的 UIWebView。初始化时有几个关键对象：

WKWebViewConfiguration 是整个配置的容器，里面最重要的是 WKUserContentController，你可以通过它注入 JS 脚本（WKUserScript），也可以注册消息处理器，让网页调用 Native 功能。

② 发起请求 & 导航拦截

调用 load(URLRequest) 后，WebKit 会先问你的 navigationDelegate：这次跳转允许吗？

这个回调是拦截跳转的最佳时机，可以阻止跳转、做鉴权、拦截自定义 scheme。

③ 网络层：DNS → TCP → HTTP

这部分由系统的 URLSession / CFNetwork 栈驱动（不是 App 的 URLSession，是 WebContent 进程内部的）：

  • DNS 解析：系统缓存优先，没缓存才真正查询。
  • TLS 握手：HTTPS 站点会走证书验证，如果服务器证书有问题，didReceive challenge 回调会触发，App 可以自定义处理。
  • HTTP 缓存：遵循标准的 Cache-Control、ETag 等缓存协议，WKWebView 有自己的磁盘缓存（WKWebsiteDataStore），不共享 App 的 URLCache，这点是常见踩坑点。

④ 响应策略

收到服务器响应头后，再问一次 delegate：这个响应允许展示吗？

如果 MIME 类型是 PDF 或其他无法渲染的内容，WebKit 会自动触发下载。

⑤ 渲染引擎：WebKit 的五步流水线

这是最核心的部分，数据到了之后 WebKit 做这些事：

  1. HTML 解析 → DOM Tree：把 HTML 字节流解析成节点树，遇到 <script> 默认阻塞解析（除非有 async/defer）。
  2. CSS 解析 → CSSOM：解析所有样式表，生成样式规则树。
  3. 合并 Render Tree：把 DOM 和 CSSOM 合并，只包含可见节点。
  4. Layout（排版）：计算每个节点在屏幕上的精确位置和大小。
  5. Paint + Composite（绘制与合成）：生成图层，交给 GPU 合成输出到屏幕。

JS 由 JavaScriptCore 引擎执行（和 Safari 共用）。图片解码是异步的，不阻塞主渲染流程。

二、APP 可以优化的点

  • 提前预热 WKWebView（第一次创建 WebView 本身需要约 200-300ms 初始化）
  • 离线包方案：把 H5 资源打包进 App，省去网络下载时间
  • 预加载：用户还没点进去，App 就偷偷在后台开始加载页面
  • 注入公共 Cookie / Token，省去 H5 自己获取登录态的时间

1. 预热 WKWebView

问题根源：第一次创建 WKWebView 时，系统需要启动 WebContent 进程、初始化 WebKit 引擎，耗时 200-300ms，用户会感觉到明显的白屏延迟。

解法：App 启动后提前创建一个 WKWebView 藏在内存里，用户真正打开页面时直接拿来用，跳过初始化耗时。

注意：预热的 WKWebView 要放在内存里，不能加到任何视图层级上，否则会影响布局。

2. 离线包方案

问题根源：H5 资源（JS、CSS、图片）每次都要从网络下载，弱网环境下可能要等 1-3 秒。

核心思路：把 H5 的静态资源提前打包下载到本地，WebView 加载时拦截网络请求，用本地文件替代网络响应。

解法：在用户”即将”打开页面之前，偷偷提前开始加载。

4. 注入 Cookie / Token

问题根源：H5 加载完成后还要自己发请求获取登录态，又多一次网络往返，慢且有闪屏风险（先展示未登录状态，再切换到登录状态）。

解法：WebView 加载之前，Native 把 Token 直接塞进去，H5 一渲染就已经是登录状态了。

三、具体优化过程

（一）现有卡点和改进思路

现在的记事本业务中（代办提醒业务也有加载 H5 的业务，但是涉及到 RN bundle 的加载，暂不考虑），点击笔记 item 都会加载对应的 H5 详情页面，从点击到完全渲染出页面体感耗时 1s+，会看到明显的 loading 动画和短暂的白屏过渡。

优化前效果：

现有的业务代码逻辑是：

MemoryListView 打开的 selectedNoteUrl 实际上是固定的 livisNotepadURL，noteId 是通过 customData 传进去的，不是每条笔记一个不同 URL。那么，完全可以提前把记事本 H5 “壳子页”预加载好，点击后直接复用这一个 WKWebView，再把当前 noteId 注入进去。这比每条 item 单独预加载一个 H5 简单很多、风险也低很多。

所以修改后的方案是：

页面进入时就预取 token + 预热 WebKit + 预加载记事本 H5 壳子 → 点击 item 时直接复用已加载好的 WebView → 注入 noteId → 展示

也就是说暂时可以先做上面优化里面的 1（预热）、3（预加载）、4（注入 Cookie） 三项优化。

（二）具体改动

要想把预加载出来的 WKWebView 真正复用到正式展示链路里，就需要修改 UILib 库。

因为当前 LivisWebViewController 最终会走 Pod 里的 WebViewController，创建自己的 wkWebView 并自动 loadRequest。如果不改 Pod，就很难把 WebViewPreloader.shared.preloadedWebView 真正塞进去复用。

一期

暂时先不做较大改动，先采用以下方案：

不再追求复用同一个预加载 WKWebView 实例（那需要改 Pod 基类），而是改成三件事：

  • 提前拿登录态：进入列表页就预取 JWT；
  • 提前种业务 Cookie：避免点击后再补登录态；
  • 提前预热 WebKit / H5 壳子页：让正式打开时尽量复用已拉起的 WebContent 进程、共享 processPool、共享 UserAgent、共享默认数据存储带来的缓存收益。

具体修改：

  • 新增记事本 H5 的统一预热配置与辅助方法到 WebViewUtils.swift，包括 notebook URL、提前种 cookie、构造与正式链路更接近的预热 WKWebViewConfiguration、为预热 WebView 设置共享 processPool 和 UserAgent。
  • 扩展 WebViewPreloader.swift，支持在预热时传入自定义 webViewConfigurator，这样就能在不碰 Pod 基类的前提下，让预热出来的 WebView 更贴近正式打开链路。最后把 MemoryListView.swift 的 prepareNotebookH5IfNeeded() 改成统一走这些工具方法，减少点击前后的配置分叉。

预期的效果：

  • 列表页进入后更早完成 JWT / cookie / WebKit 进程 / UserAgent / 共享 processPool 预热；
  • 点击笔记 item 时，正式 WebView 能复用更多进程与缓存收益，减轻冷启动白屏；
  • 所有改动都在 Swift 层，不改 Pod。

优化后效果：

速度快的话会看不到 loading 动画，但是还是会有白屏间隙时间。
