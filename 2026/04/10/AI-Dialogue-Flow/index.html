全链路 AI 对话系统架构解析：VAD · ASR · LLM · TTS · RTC

发表于 2026-04-10 分类于 AI架构设计
本文拆解端到端 AI 对话系统的全链路五层架构，从 VAD 门控、ASR 语音识别、LLM 推理，到 TTS 合成与 RTC 实时传输，分析各层核心设计取舍与延迟优化要点，端到端延迟目标 < 800ms。

一个端到端的 AI 语音对话系统，远不止是”说话 → AI 回答”这么简单。在用户开口到听到回复的 800ms 以内，系统需要依次完成语音检测、语音识别、大模型推理、语音合成和实时传输五个关键环节。

本文以下图架构为脉络，逐层拆解每一层的核心设计思路和关键技术取舍。

全链路五层架构

第一层：VAD · 语音活动检测

这是整个管道的门控。麦克风持续采集音频，VAD 以约 30ms 为帧长，实时判断当前帧是否包含人声——核心解决两个问题：

  • 用户开始说话了：触发 ASR 开始工作
  • 用户说完了：endpoint detection，触发后续推理

常用方案有 WebRTC 内置 VAD 和 Silero VAD，误检率直接影响交互体验。

第二层：ASR · 自动语音识别

将语音帧转换为文字 token，现代 ASR 分三步走：

  1. 用 Mel 频谱提取声学特征
  2. 通过 Transformer / Conformer 架构做序列建模
  3. 用 CTC 或 Beam Search 解码出文本

关键设计取舍在于流式 vs 离线——流式 ASR（如 FunASR 的实时模式）能在用户说话时就输出中间结果，大幅降低首包延迟，但准确率略低；Whisper 是非流式的高精度代表。

第三层：LLM · 大语言模型推理

这是系统的”大脑”。文本进入 LLM 后，模型依据 System Prompt、对话历史（Memory）和可选的 RAG 知识库来生成回复。

影响延迟的核心技术：

  • KV Cache：避免重复计算注意力，显著提升吞吐
  • 流式输出（Streaming）：生成一个 token 就发给 TTS，而不是等全部生成完再发

复杂场景下还会触发 Function Calling / Agent 行动，通过 MCP 协议调用外部工具后再汇总回答。

第四层：TTS · 语音合成

把文本转回人声，流程是：

文本前端（分词 + 韵律预测 + G2P 音素转换）→ 声学模型（VITS / FastSpeech2 预测 Mel 频谱）→ 声码器（HiFi-GAN / WaveNet 还原 PCM 波形）

现代 TTS 支持零样本音色克隆（仅需 3 秒参考音频），以及与 LLM 联动的情感 / 语速控制。

流式 TTS 的关键在于：拿到 LLM 第一句话后就立刻开始合成，不等全文，这是控制端到端延迟的核心手段之一。

第五层：RTC · 实时音频传输

合成好的音频经 WebRTC + Opus 编码发回客户端播放。这一层还承担打断检测的职责——

当用户在 AI 说话过程中插话，VAD 检测到后立刻中止当前 TTS 播放，清空队列，将新语音送入 ASR，实现真正的全双工对话。同时，RNNoise 在传输层做实时降噪，进一步保障语音质量。

端到端延迟拆解

层级 典型延迟
VAD ~30ms
ASR ~200ms
LLM ~300ms（首 token）
TTS ~200ms
RTC ~50ms
合计 < 800ms

每一层的流式化改造都是压缩整体延迟的关键——ASR 流式输出、LLM 流式推理、TTS 流式合成，三层叠加才能把端到端延迟控制在体验可接受的范围内。
