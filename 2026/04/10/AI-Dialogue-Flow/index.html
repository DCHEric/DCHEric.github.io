全链路 AI 对话系统架构解析：VAD · ASR · LLM · TTS · RTC

PUBLISHED 2026.04.10
RTC ASR TTS LLM AI Agent 实时对话

ChatGPT、豆包、千问……这些正在被亿级用户使用的大语言模型对话应用，其语音交互功能背后，大多跑的是一套由 VAD、ASR、LLM、TTS、RTC 串联而成的端到端 AI 对话管道——至少在一两年前是这样。

表面上看，用户说一句话，AI 回一句话。但在这 800ms 内，系统至少要串联五个异构子系统——VAD、ASR、LLM、TTS、RTC——每一层都有独立的延迟曲线、失败模式和流式化策略。任何一层拖慢了，整体体验就会崩塌。

本文以下图架构为主线，逐层拆解各层的工作机制、关键设计取舍，以及在工程落地中容易踩到的坑。

一、为什么这个系统难做

在展开各层之前，先建立一个整体认知：这套系统的核心难点不在某一层，而在”流式”二字贯穿全链路。

传统软件的请求-响应模型是：等输入完成 → 处理 → 返回结果。但 AI 对话系统要求：

  • 用户没说完，ASR 就要开始输出中间结果
  • ASR 没结束，LLM 就要开始推理
  • LLM 没生成完，TTS 就要开始合成
  • TTS 没播完，用户随时可以打断

每一层都在”半成品”状态下驱动下一层。这意味着，你不仅要把每层做对，还要把层与层之间的流式接驳和状态同步做对。

二、全链路五层架构

第一层：VAD · 语音活动检测

VAD（Voice Activity Detection）是整个管道的门控，也是最容易被低估的一层。

它在做什么

麦克风持续采集 PCM / AAC 原始音频流，VAD 以约 30ms 为帧长，对每一帧做二分类判断：

  • 当前帧是有效语音（human speech）→ 继续送入 ASR
  • 当前帧是背景噪声 / 静音 → 丢弃，等待下一帧

VAD 实际上要解决两个截然不同的问题：

问题 描述 触发动作
语音起点检测（Voice Start） 用户开始说话了 唤醒 ASR，开始送帧
语音终点检测（Endpoint Detection） 用户说完了（停顿超过阈值） 通知 ASR 结束本轮，触发 LLM 推理

终点检测（Endpointing）是体验的关键。判太快，会截断用户还没说完的话；判太慢，AI 反应迟钝，对话节奏变死板。通常设置 300～600ms 的静音窗口，结合语境动态调整。

两种主流实现

WebRTC 内置 VAD：基于 GMM（高斯混合模型）的传统方案，计算极轻，延迟 < 5ms，适合嵌入式和低功耗场景，但在嘈杂环境下误检率偏高。

Silero VAD：基于神经网络（LSTM）的现代方案，8kHz / 16kHz 均支持，对音乐、空调、餐厅背景噪声的鲁棒性显著优于 WebRTC VAD，推理开销约 1ms/帧，是目前生产环境的主流选择。

工程细节

VAD 的误检（false positive）和漏检（false negative）对体验的影响是不对称的：

  • 误检（把噪声当人声）：ASR 收到无效帧，产生幻觉文本，LLM 被错误触发
  • 漏检（把人声当噪声）：用户的话被截断，体验极差

实践中通常对”语音起点”用低阈值（宁可多触发），对”语音终点”用高阈值 + 滑动窗口（避免提前截断）。

第二层：ASR · 自动语音识别

ASR（Automatic Speech Recognition）将连续语音帧转换为文字 token，是感知层（PERCEPTION）的核心。

现代 ASR 的三步流水线

① 声学特征提取

原始 PCM 波形先经短时傅里叶变换（STFT），映射到 Mel 频谱（梅尔频谱图）。Mel 尺度模拟人耳对频率的非线性感知，80 维 Mel 特征可以在保留语音核心信息的同时大幅压缩数据量。

② 序列建模

Mel 特征送入 Transformer / Conformer 架构。Conformer 是 Transformer + 卷积的混合体，卷积分支捕捉局部音素边界特征，Transformer 分支建模长距离依赖，二者结合在语音任务上表现优于纯 Transformer。

③ 解码输出

模型输出 logits 后，有两种解码策略：

  • CTC（Connectionist Temporal Classification）：允许输出”空白符”，帧级别对齐，速度快，适合流式场景
  • Beam Search + 语言模型融合：准确率更高，但延迟较大，适合非实时场景

流式 vs 离线：核心取舍

维度 流式 ASR（FunASR 实时模式） 离线 ASR（Whisper）
首包延迟 极低，边说边出字 需等待完整语音
准确率 略低，中间结果不稳定 高，尤其多语言
适用场景 实时对话、语音助手 会议转写、字幕生成
典型模型 FunASR、Paraformer-Streaming Whisper large-v3

流式 ASR 会持续输出中间假设（partial hypothesis），在用户还在说话时就把文字送给 LLM 预热上下文，是压缩端到端延迟的关键手段。

几个工程细节

  • 热词（Hotword）注入：产品名、专有名词可通过热词列表或提示词方式偏置解码，减少误识别
  • 标点恢复：ASR 输出通常没有标点，需要额外的标点恢复模型，或者依赖 LLM 在推理时处理
  • 语言检测：多语言场景下需要前置语种识别，或直接使用 Whisper 的多语言模型

第三层：LLM · 大语言模型推理

LLM 是系统的”大脑”，负责理解意图、维护对话状态、生成回复。从架构图看，这一层内部分为三个子模块。

子模块一：上下文管理

每次 LLM 推理时，输入不只是用户当前说的话，而是一个精心构造的 Context Package：

Memory 管理是长对话场景的核心挑战：Context Window 有限，轮数多了就需要做摘要压缩或关键信息提取，决定”哪些历史值得保留”。

RAG（检索增强生成） 让 LLM 能引用实时、私有的知识，而不只依赖训练数据。典型实现是向量数据库（Faiss / Milvus）+ 语义检索，召回 Top-K 相关文档后拼入 Prompt。

子模块二：推理生成

LLM 自回归地逐 token 生成文本，两项关键优化直接影响延迟：

KV Cache：注意力机制每次都需要计算所有历史 token 的 Key / Value 矩阵。KV Cache 把已经计算过的 K/V 缓存下来，新 token 只需增量计算，推理速度可提升数倍。

流式输出（Streaming）：不等 LLM 生成完整回复，每生成一个 token（约 10～30ms 一个）就立即推送给 TTS。这样 TTS 可以在 LLM 还在推理时就开始合成第一句话的音频，两层并行大幅压缩感知延迟。

子模块三：工具调用

当用户意图需要查数据库、调 API、执行代码时，LLM 会输出结构化的 Function Call 指令，而不是直接生成文字回复：

MCP 协议（Model Context Protocol） 是 Anthropic 推出的工具调用标准，定义了 LLM 与外部工具之间的标准化接口，让 Agent 能够以统一方式调用文件系统、数据库、API 等异构资源。

工具调用会引入额外一次网络 RTT，在对话场景中需要特别关注超时处理和降级策略——工具调用失败时，LLM 应该能够优雅回退，而不是沉默或报错。

第四层：TTS · 语音合成

TTS（Text-to-Speech）是输出层（OUTPUT）的核心，把 LLM 生成的文字还原为自然语音。

三级流水线

① 文本前端

原始文本经过：

  • 分词（Tokenization）：切分词边界
  • 韵律预测（Prosody Prediction）：预测停顿、重音、语调
  • G2P（Grapheme-to-Phoneme）：将文字转为音素序列，处理多音字、英文缩写、数字读法等

文本前端是中文 TTS 的难点——“重要”可以读 zhòng yào 也可以读 chóng yào，”一”在不同语境下变调规则复杂，都需要在这里处理正确。

② 声学模型

将音素序列映射为 Mel 频谱图，主流架构：

  • FastSpeech2：非自回归，并行生成，速度快，但音色自然度略低
  • VITS（Variational Inference with adversarial learning for TTS）：端到端模型，直接从文本生成波形，音质更自然，推理相对较慢

③ 声码器（Vocoder）

将 Mel 频谱还原为 PCM 音频波形：

  • HiFi-GAN：基于 GAN 的高保真声码器，推理速度快，可实时合成
  • WaveNet：自回归生成，质量极高，但速度慢，已逐渐被 GAN 系替代

音色克隆与情感控制

现代 TTS（如 CosyVoice、Edge-TTS）支持零样本音色克隆——只需提供 3 秒参考音频，模型即可提取说话人的音色特征，用于后续合成。这让产品可以”定制专属 AI 声音”。

结合 LLM 的语义理解，TTS 还可以做情感控制：在 System Prompt 中指定情感类型（兴奋、温柔、严肃），或让 LLM 在输出文本时插入情感标记（如 <emotion=happy>），TTS 据此调整语速、音调和停顿。

流式 TTS 的关键设计

对话场景中，TTS 不能等 LLM 输出全文再合成——那样延迟会直接叠加。正确做法是：

  1. LLM 输出第一个自然段落边界（句号、逗号、换行）时，立刻把这一段送给 TTS
  2. TTS 开始合成第一段的同时，LLM 继续生成后续文字
  3. 第一段音频播放完毕时，第二段往往已经合成好进入队列

这种分段流式合成 + 音频队列的设计，可以把 TTS 感知延迟压缩到 200ms 以内。

第五层：RTC · 实时音频传输

RTC（Real-Time Communication）是传输与交付层（DELIVERY），负责把合成好的音频低延迟送达客户端，同时承担全双工打断的协调职责。

音频传输

WebRTC + Opus 是目前的行业标准组合：

  • WebRTC：提供 P2P / 中转服务器模式的实时传输，内置抖动缓冲（Jitter Buffer）和丢包重传（NACK）
  • Opus：可变比特率语音编码，20ms 帧长，在 6～510kbps 宽范围内维持高质量，对网络波动的鲁棒性远优于 MP3 / AAC

低延迟回放：客户端接收音频后，通过自适应播放缓冲（通常 50～80ms）平滑网络抖动，同时保持端到端延迟可控。

RNNoise 降噪：在传输层对麦克风输入做实时降噪，基于 RNN 的频域降噪，能有效压制空调、键盘、背景音乐等噪声，让 VAD 和 ASR 收到更干净的语音信号。

全双工打断机制

这是整个系统中工程复杂度最高的部分，也是区分”玩具级”和”产品级”对话系统的核心标准。

场景：AI 正在播放回复，用户突然插话说”等一下，我换个问题”。

正确的处理流程：

工程挑战：

  • 信令与媒体的同步：打断信令走控制通道，音频走媒体通道，两者延迟不同，需要在客户端做时间戳对齐，避免”信令到了但音频还在播”的撕裂感
  • LLM 推理取消：大多数 LLM API 支持 AbortController 或 SSE 连接关闭来中断推理，但 GPU 上已经在跑的推理无法立即停止，需要接受一定的”尾巴”延迟
  • 上下文修复：被打断的那半句话是否计入对话历史？通常的做法是：如果 AI 说完了 30% 以上，把已说内容摘要后加入 Memory；否则直接丢弃

三、端到端延迟拆解

层级 典型延迟 流式优化空间
VAD ~30ms 无需优化，本身已足够快
ASR ~200ms 流式输出，首字延迟可压到 100ms
LLM ~300ms（首 token） KV Cache + 流式推理
TTS ~200ms 分段流式合成，首段可压到 150ms
RTC ~50ms 自适应缓冲控制在 50ms 内
合计 < 800ms 各层流式化后可接近 400ms

800ms 是业界公认的”体验临界点”——超过这个延迟，用户会明显感到”AI 在思考”，对话节奏变得不自然；低于 400ms，用户几乎感知不到延迟，交互体验接近真人通话。

压缩延迟的核心杠杆只有一个：让每一层都在”半成品”状态下驱动下一层启动，而不是等上一层完全完成再交接。

四、工程落地中的典型问题

问题一：ASR 中间结果污染 LLM 上下文

流式 ASR 的中间结果不稳定，同一段话可能先输出”我想要一个苹果”，后修正为”我想要一个平板”。如果直接把中间结果送给 LLM，会产生大量噪声推理。

解法：区分 partial（中间结果，用于预热）和 final（终态结果，用于正式推理），只把 final 结果写入对话历史。

问题二：TTS 分段切割破坏韵律

LLM 输出按标点分段后送给 TTS，如果切割粒度太细（如每个逗号都切一次），每段之间会有明显的合成接缝感，听起来断断续续。

解法：设置最小分段长度（如 20 个字），短于阈值的片段合并到下一段再合成；同时在段与段之间使用 crossfade 平滑过渡。

问题三：网络抖动导致音频卡顿

移动网络下 RTC 传输的抖动（Jitter）可能达到 100ms 以上，如果播放缓冲设置太小，音频会频繁卡顿。

解法：动态调整 Jitter Buffer 大小——网络好时收紧到 30ms，网络差时自动扩大到 150ms，同时通过 PLC（Packet Loss Concealment）对丢包帧做插值补偿。

问题四：多轮对话的 Context 膨胀

对话轮数增加时，拼入 LLM 的 Context 越来越长，推理延迟线性增长，最终超出 Context Window 上限。

解法：设定滑动窗口（如保留最近 10 轮），对更早的历史做渐进式摘要——每隔 5 轮，用 LLM 把前 5 轮压缩成一段摘要，追加到 System Prompt 末尾，既保留关键信息，又控制 Token 消耗。

五、端侧小模型的机会

上述架构的每一层，都可以有端侧（On-Device）替代方案：

  • VAD：Silero VAD 的 ONNX 版本，模型 < 2MB，手机端实时运行
  • ASR：Whisper tiny / base，量化后 < 100MB，可离线识别
  • LLM：VoxCPM2 是面壁智能联合清华大学人机语音交互实验室开源的 2B 对话小模型，专为端侧语音交互优化，支持直接理解语音输入，不需要独立 ASR 层
  • TTS：Edge-TTS、CosyVoice 轻量版均支持端侧部署

端侧方案的核心价值在于：零网络延迟、离线可用、隐私保护。代价是模型能力弱于云端大模型，适合对延迟和隐私要求极高、但对回复复杂度要求相对较低的场景（如智能耳机、车载助手）。

六、下一代方向：端到端音频大模型

上述五层管道是一套模块化架构——每一层独立可替换，工程上清晰可控。但它有一个根本性的信息损耗问题：

用户说话时的语气、情绪、停顿、语调，在经过 ASR 转成文字的那一刻，就全部丢失了。LLM 只能读到文字，对”这句话是疑问还是感叹、是平静还是愤怒”一无所知。

这推动了新一代端到端音频语言模型（Speech Language Model）的出现。

核心思路：把 ASR 和 TTS 融进模型内部

不再把语音转成文字再处理，而是让模型直接理解音频 token、直接生成音频 token。

语音信号被切分为离散的音频 token（通过 EnCodec / SoundStream 等神经编码器），直接送入 Transformer 进行建模，输出也是音频 token，再解码为波形。整个过程中文字只是一个可选的中间表示，不再是必须的信息通路。

代表产品

GPT-4o Advanced Voice Mode

OpenAI 在 2024 年推出的高级语音模式是目前最具代表性的端到端实现。GPT-4o 原生支持音频输入和音频输出，模型同时理解语义、语气和情绪，可以在对话中自然地笑、叹气、被打断，响应延迟接近 200ms，远低于传统管道的 800ms。

Qwen2-Audio（通义千问音频版）

阿里巴巴的 Qwen2-Audio 是一个多模态模型，支持直接理解音频输入——不仅是对话语音，还包括音乐、环境声、说话人情绪识别等。对话场景下绕过独立 ASR，直接从音频推理生成文字或语音回复。

Moshi（Kyutai）

法国 AI 实验室 Kyutai 开源的 Moshi 是首批真正意义上的实时语音对话大模型之一，支持全双工——用户说话时模型可以同时”思考”并插话，模拟人类对话中的自然交叠，而不是严格的”你说完我再说”。

与传统管道的对比

维度 模块化管道（本文主体） 端到端音频大模型
架构 VAD + ASR + LLM + TTS + RTC 串联 单一音频语言模型
延迟 ~800ms ~200ms
情感理解 丢失（文字无情绪信息） 保留（直接处理音频）
打断处理 需要额外信令协同 模型原生支持全双工
工程可控性 高，各层独立可调 低，黑盒难以干预
部署成本 各层可独立优化/替换 需要完整模型推理
当前成熟度 高，已大量生产落地 较低，仍在快速演进

还不能完全替代的原因

端到端模型目前有几个明显短板：

  • 幻觉问题更难排查：传统管道可以在 ASR 输出、LLM 输出等节点逐层 logging 和干预；端到端模型出错时难以定位是哪个环节的问题
  • 专业领域适配成本高：模块化管道可以单独替换 ASR 热词、LLM System Prompt、TTS 音色；端到端模型需要整体微调
  • 音频 token 效率：语音 token 的密度远低于文字 token，同样长度的对话，音频 token 数量是文字的数十倍，推理成本显著更高
  • 多语言和方言支持：文字模态有海量训练数据，音频模态的覆盖度仍在追赶

短期内，模块化管道和端到端模型会长期并存——前者在 B 端、定制化、对可控性有要求的场景中仍是主流；后者在追求极致体验的 C 端消费产品中快速渗透。
